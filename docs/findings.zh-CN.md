# Codex 满载自救：从「模型满载」到请求瘦身

> 原始诊断文档，来自 [NewBeeM4n/codex-overload-fix](https://github.com/NewBeeM4n/codex-overload-fix)（MIT）。
> 文中的端口（8787）和 provider 名（`openai-retry`）是原始版本的写法；本衍生版在
> cockpit-tools 布局下默认用 8788 与 `codex_local_access_retry`，见 `docs/cockpit-notes.md`。
>
> 2026-10-23 实测复盘。适用于桌面版 / CLI 版 Codex 出现频繁 `Selected model is at capacity. Please try a different model.` 的情况。

**结果先说**：改之前根本干不了活——基本上每两轮就被 cap 打断，一个需要多轮工具调用的任务连开场都跑不完。改之后，同样的任务从头跑到尾，交付了完整结果——就是下面第五节那份数据。

这不是"体验变好"，是**从不可用变成可用**。

---

## 一、先排除三个错误答案

这个报错很能带偏人，我逐项实测排除了：

- **不是网络。** 五个不同地区、不同运营商的出口节点交错测试，30 次真实请求全部成功，零 Cloudflare 挑战页。
- **不是账号被风控。** 失败那次的响应头是 `x-codex-plan-type: plus`、`x-codex-primary-used-percent` 远低于上限 —— 额度几乎没动。
- **不是模型真的满载。** 同一分钟、同一节点里，小请求照常通过，大请求被拒。

真正的证据：这个错误不是 HTTP 5xx，而是**一个 HTTP 200 响应里的 SSE 事件**，客户端读完整条流才判定失败：

```json
{"type":"error","sequence_number":3,
 "error":{"type":"service_unavailable_error",
          "code":"server_is_overloaded",
          "message":"Our servers are currently overloaded. Please try again later."}}
```

这个区别很关键：如果是 5xx，客户端和代理层都会自动重试；但包在 200 里，只有**认得出这个事件**的人才会重试。

---

## 二、原理：按时间窗丢包，按体积加权

服务端的准入层不是「模型满了」，而是**在特定时间窗里批量丢弃请求**，好窗口里再按模型分流。

同一节点交错跑 8 轮：
- `gpt-5.6-terra`：8/8 通过
- `gpt-6.1-sol`：只有 5/8

更关键的是**体积相关性**。手工构造 684 KB 提示词连跑 6 次，33% 被拒；同机、同时间的小请求只有 10%。也就是说请求越大越容易被丢 —— 而桌面版 Codex 的请求天生就大。

**一句话：不是请求错了，是请求太大，而且没人替你重试。**

客户端默认只重试 5 次，失败后直接把错误弹给你，所以体感是「根本没法用」。而另一条走反代的路径两小时只报 5 次错、活照干，差别就在重试层。

### 顺带说一句：这个设计哪里不对

有人会问，为什么不能排队？答案是**排队在规模下会更糟**——容量不足时如果有队列，到达速率持续高于处理速率，队列会无限增长；客户端超时重试，重试带来更多流量，最后一起雪崩。所以**快速丢弃、让客户端退避**是工业界的标准做法，机制本身没错。

错的是**丢的方式**：

| 现在的问题 | 应该怎样 |
|---|---|
| 错误藏在 HTTP 200 的 SSE 流里 | 返回 **503 + `Retry-After`**，让所有代理和网络库都能处理 |
| 没有 `Retry-After` | 告诉客户端该等 2 秒还是 2 分钟 |
| 客户端默认只重试 5 次 | 这类错误应该默认重试，预算远高于 5 次 |
| 提示「换个模型试试」 | 对体积型准入来说这是**误导**，换模型解决不了 |

一句话：**该丢就丢，但得丢得响亮。** 现在的做法是把人推进河里，还不让他喊。

## 三、杠杆 A：本地重试中继

最直接的想法是调大 Codex 的重试次数，但内置 provider `openai` 是保留 ID，写进 `model_providers` 会直接报错：

```
model_providers contains reserved built-in provider IDs: openai
```

**绕法**：自建一个 provider，指向本机的重试中继。

```toml
model_provider = "openai-retry"

[model_providers.openai-retry]
name = "OpenAI (retry)"
base_url = "http://127.0.0.1:8787"
wire_api = "responses"
requires_openai_auth = true      # 复用现有 OAuth，不用重新登录
stream_max_retries = 20
request_max_retries = 10
```

`requires_openai_auth = true` 会让 Codex 照常带上原有的 ChatGPT Bearer token 和账号头，**套餐、用量、登录状态都不受影响** —— 中继只是多了一跳 TCP。

中继本身是一个 Python 单文件（只用标准库），监听 8787，转发到官方端点。核心是两件事：认出 overload，以及在安全的时机重试。

```python
OVERLOAD = {
    "server_overloaded",       # response.failed 里的 code
    "server_is_overloaded",    # 裸 error 事件里的 code（真实流量是它）
    "service_unavailable_error",
}

# 只有还没吐出任何内容时才允许重试
COMMIT = {
    "response.output_text.delta",
    "response.reasoning_summary_text.delta",
    "response.output_item.done",
    "response.completed",
}
```

### 三条安全规则，缺一不可

1. **只在没出字时重试。** 一旦有 `output_text.delta` 或 reasoning 摘要落地，就直接放行原流 —— 否则会生成两遍。
2. **退避带抖动。** 1 秒起、上限 8 秒、乘 1.6 递增并加 0.7~1.3 的随机抖动，最多 30 次 / 300 秒预算。
3. **客户端走了就停。** 用 `select` + `MSG_PEEK` 探测本地 socket，Codex 取消或退出时立即放弃重试，不空烧额度。

> Windows 注意两点：`schtasks` 建计划任务需要管理员权限，普通账户用 `HKCU\...\Run` 更省事；`powershell -WindowStyle Hidden` 挡不住控制台窗口，必须用 `wscript` + `SW_HIDE` 起一个 VBS 启动器。

## 四、杠杆 B：请求瘦身

抓包拆开一个完整的桌面版请求（新会话，89,240 字节），每一轮都会重发这些：

| 组成 | 体积 | 能砍 |
|---|---|---|
| 工具定义 `additional_tools` | 27,599 B | 否 |
| 基础系统提示 | 17,730 字符 | 否 |
| 技能清单（72 个技能） | 20,369 字符 | **是** |
| 记忆块 | 12,827 字符 | **是** |
| 团队 / 多智能体提示 | 2,819 B | 否 |
| 环境上下文 + 用户这句话 | 821 B | — |

把 37 个自装技能和四个非原生插件砍掉后：**89,240 → 71,380 字节（-20%）**，技能清单从 72 个降到 10 个。

> **踩坑记录**：远程插件直接删缓存没用，App 一启动就会重新下载。能卸的走 `codex plugin remove 名字@市场名`；服务端拒绝卸载的（返回 `Installed-by-default plugins cannot be uninstalled`），在 config 里写 `[plugins."名字@市场名"] enabled = false`，重新下载后也不会加载它的技能。

**真正的大头其实是会话历史。** 桌面版自己的日志里 `pre_compression_bytes ≈ 724,000`，而新会话只要 89 KB 起 —— 差的那 600 多 KB 全是这个会话累积下来的。所以最有效的单步操作是**开会话**，不是删记忆。

## 五、实测：24 个请求，0 次失败

一个真实任务（约 8 分钟，含生成与多轮工具调用）经中继的全部请求：

| 时间 | 体积 | 尝试 | 结果 |
|---|---|---|---|
| 17:38:20 | 775 KB | ×3 | 成功（连撞 2 次，43 秒） |
| 17:38:55 | 90 KB | ×2 | 成功 |
| 17:40:52 | 123 KB | ×2 | 成功 |
| 17:41:40 | 90 KB | ×3 | 成功 |
| 17:42:43 | 155 KB | ×2 | 成功 |
| 17:42:58 | 96 KB | ×2 | 成功 |
| 17:43:20 | 160 KB | ×2 | 成功 |
| 其余 17 条 | 60–183 KB | ×1 | 一次通过 |

总计 **24 个请求、9 次重试、0 次放弃、0 次弹到用户面前**。

最夸张的那条 775 KB 连撞两次 overload，第 3 次成功 —— 用户只看到它在思考。

### 第二个任务，数据更狠

当晚又跑了一个动画任务，情况比第一个极端得多。三条 770 KB 左右的大请求在**同一秒**打出去，结果：

| 请求体 | 大小 | 尝试次数 | 结果 |
|---|---|---|---|
| 任务请求 A | 799 KB | **9 次** | 成功 |
| 任务请求 B | 769 KB | **8 次** | 成功 |
| 后台请求 | 769 KB | **7 次** | 成功 |
| 正常轮次 ×4 | 65–99 KB | 1–3 次 | 成功 |

那条 799 KB 的请求连续失败 8 次、每次间隔 1–8 秒，第 9 次才拿到流——**用户全程看到的是"正在思考"**。

把当晚全部 71 个请求按体积归桶，规律**不是渐变，是断崖**：

| 请求体 | 条数 | 平均尝试次数 | 最惨 |
|---|---|---|---|
| < 100 KB | 20 | 1.95 | 5 |
| 100–200 KB | 24 | 1.96 | 9 |
| 200–500 KB | 23 | 1.74 | 4 |
| **> 500 KB** | **4** | **6.75** | **9** |

500 KB 以下，各档几乎不可区分，都落在 1.7–2.0；跨过 500 KB，均值直接跳到 6.8。430–768 KB 之间没有样本，所以确切阈值还定不下来。

合计 **82 次重试、0 次放弃**。

两点值得注意：

1. **并发会叠加。** 最坏情况是同一秒发出三个大请求，它们互相挤占准入槽位。这更像"按分钟窗口限量"，而不是单请求随机。
2. **大请求往往是任务的开场白。** 带参考图的任务，第一轮就可能是 700+ KB——而这一轮恰恰最不能失败。压缩图片比什么都管用。

### 一个没刻意设计的对照实验

手上有第二台设备，**同一个账号、同一个网络**，Codex 是原装配置——没中继、没瘦身。同一个晚上：

|  | 修过的机器 | 没修的机器 |
|---|---|---|
| 账号 / 出口 | 同一个 | 同一个 |
| 时间段 | 同一晚 | 同一晚 |
| 表现 | 一整晚一次短暂提示 | 每几轮就 cap |

同账号、同出口、同时间窗，唯一变量是本地配置。这就排除了账号级限流、额度、区域，以及“服务器刚好恢复了”。

还有一个更反直觉的数字：修过的机器上，中继在**某 12 分钟内吞掉了 25 次重试**。

> **服务端的压力根本没降，你只是看不见了。**
> 你不是运气变好了，是有人在替你挨打。

> 那条 775 KB 的构成很特别：`msg:developer` 只有 3,461 字节，而正常工作轮次是 28~56 KB。说明它不是普通对话，而是带大块附件（大概率是截图）的请求 —— 这类请求最容易被拒，值得单独关掉来源。

## 六、操作清单

1. 写一个本地中继，监听 `127.0.0.1:8787`，转发到 `chatgpt.com/backend-api/codex`。
2. 在 `config.toml` 里加自定义 provider，并把 `model_provider` 指过去（改前备份）。
3. Windows 用 VBS + `HKCU\...\Run` 做无窗自启，再加一个每 30 秒检查端口的看门狗。
4. 砍掉不用的技能和插件；记忆块按需保留。
5. 老会话换成新会话 —— 这是单项收益最大的一步。

## 七、这些别试了

每一条都实测过，对容量报错没有影响：

| 做法 | 实测结果 |
|---|---|
| 换代理服务商 / 换节点 | 五个不同出口 30/30 成功，被拒率不变 |
| 换模型 | 好窗口里 terra 略优；坏窗口里所有模型一起挂 |
| 改系统时区 | 连改 5 次，报错频率毫无变化 |
| 改 `service_tier` | default / priority 交替 8 组，无差别 |
| 重启 App | 只影响运气，不影响概率 |

## 八、风险与回滚

- 中继**只做重试**：请求体、鉴权头、SSE 内容全部原样转发，不修改、不缓存、不共享凭证。
- 它是本机进程、纯标准库，出问题删掉 `model_provider` 那行就回到官方直连。
- 脚本里如果打日志，记得把 `Authorization` 头打码。
